Getting started

Install the CLI, sign in with your own Microsoft account, and get a searchable, conflict-checked settings index for one tenant — no Azure app registration needed for solo use.

Install

Both installers download a standalone binary — no Node.js required.

Windows
$ irm https://intuneatlas.com/install.ps1 | iex
Linux
$ curl -fsSL https://intuneatlas.com/install.sh | bash

Either one puts intuneatlas on your PATH. See the CLI reference for every command it adds.

Sign in and run your first scan

  1. Run: 
    $ intuneatlas ui --tenant contoso.onmicrosoft.com
  2. A browser window opens to a normal Microsoft sign-in screen. Sign in with your own account — IntuneAtlas ships with a shared, multi-tenant app registration, so there's no Azure app of your own to set up. It requests four read-only Graph scopes: DeviceManagementConfiguration.Read.All, DeviceManagementManagedDevices.Read.All, Organization.Read.All, and DeviceManagementServiceConfig.Read.All.
  3. Once signed in, the scan runs and the web UI opens automatically at http://localhost:7878. Reopening ui later reuses the cached sign-in on Windows and macOS; on Linux it prompts again each time — a limitation of the underlying credential cache there, not something IntuneAtlas controls.
Admin consent. If your tenant requires admin consent for new app permissions, a Global or Intune admin will need to approve the request — this happens once per tenant, as part of the same sign-in prompt.

What you get

The web UI shows every Windows Settings Catalog, compliance, and enrollment setting from the scan, merged and keyed on its CSP path — with conflicts between overlapping policies and coverage gaps against a baseline surfaced directly, instead of buried across per-policy views.

It's read-only end to end: IntuneAtlas never writes anything back to the tenant.

Sharing it with a team

--host 0.0.0.0 turns the same server into a shared instance — everyone who connects signs in with their own Microsoft account, and viewing an already-scanned report needs no Intune permission at all; only triggering a new scan does.

Shared mode needs a real HTTPS hostname reachable by your teammates' browsers — Entra requires the sign-in redirect to be either https:// or exactly http://localhost, so a plain LAN IP over HTTP won't work. A reverse proxy with a certificate (Caddy is the simplest option) or any host that terminates TLS for you both work.

--persist registers that exact command to keep running across reboots — a Scheduled Task on Windows, a systemd service on Linux. See the CLI reference for the full flag list.
