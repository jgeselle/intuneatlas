What it reports

Six states. Two of them are quiet.

Every setting in the index lands in exactly one. Settings that meet a baseline, or that no baseline covers, stay out of the way, so the output is a worklist rather than a wall of green ticks.

Conflict

Two policies disagree

Same setting, different values, reaching the same group. Policies for different groups can differ without it counting. Each policy is shown with its value and who it's assigned to.

Below baseline

Weaker than the benchmark

Checked against whichever baselines you have active. Every finding names the baseline and carries its rationale, not just a severity.

Missing

Expected, set nowhere

A baseline has a rule for a setting that no policy in the tenant configures at all.

Not assigned

Configured, reaching nothing

The profile looks healthy in the portal but targets no group. Silent, and invisible in every per-policy view.

Meets baseline

Checked and passing

At least one active baseline covers the setting, and every rule that does is satisfied.

Not checked

No rule has an opinion

No active baseline covers the setting, so its value is shown but not judged either way.

Baselines

A baseline is a policy you exported.

Any Settings Catalog or compliance policy exported from Intune works as a baseline, exactly as exported: the Open Intune Baseline, a CIS build, or the policies of your own reference tenant. Nothing is converted, and nothing ships with the app.

Choose the downloaded folder on the Baselines page, or drop it into your baselines folder yourself. Settings are matched by Intune's own setting ID and compared value by value, sub-settings included.

~/.intuneatlas/baselines/ folder 
oib/
  windows-v4.0/                 # one baseline
    baseline.yml                # optional
    SettingsCatalog/
      Win - OIB - ES - Defender Antivirus - D - AV Configuration - v4.0.json
      Win - OIB - ES - Encryption - D - BitLocker (OS Disk) - v3.7.json
      …
  windows-v3.8/                 # an older version, side by side
oib/windows-v4.0/baseline.yml yaml 
name: Open Intune Baseline – Windows v4.0
settings:
  device_vendor_msft_policy_config_update_deferqualityupdatesperiodindays:
    compare: atMost        # this number or less
    severity: high
    rationale: >
      Deferring quality updates much beyond a week leaves patched
      vulnerabilities open for longer than necessary.
    reference: CIS Microsoft Windows 11 Benchmark, L1
  device_vendor_msft_policy_config_experience_allowcortana:
    ignore: true           # leave this setting out
Annotations

An exported policy says what a setting should be, not why. The optional baseline.yml adds severity, rationale and references per setting without changing the stored values, and can relax a number to "or less" or "or more".

Run it

Open it, query it, or wire it into CI.

One index, four entry points. The default command builds it and serves it on localhost; the rest hand you a single value, a file, or an exit code instead.

Read the index

Web UI — intuneatlas ui

Every setting grouped by category, searchable by CSP path, with the policies that set it, each value editable with Intune's own options and ranges, note threads, and a history of what changed between scans. Configuration and compliance policies both, for the whole tenant or one group. Staged changes pass a review gate, and an Admin can push them to Intune. Runs on your machine against the report on disk, or hosted for a team as an Azure Container App.

Single value

get — intuneatlas get <path>

One setting, every profile that sets it, and each value. Five lines of output, pipeable, no index served and no browser opened.

Scheduled

Headless scan

JSON or SARIF to disk and a non-zero exit when the tenant drifts past your threshold. The Docker image takes an app registration from the environment.

Continuous

GitHub Action

The headless scan on a cron, with findings as PR annotations. Fails the run at your chosen severity.

scheduled run — sarif to disk, non-zero on drift 
$ intuneatlas scan --baseline cis-l1 --fail-on high --format sarif

  41 policies · 1,847 settings · 11 findings (3 critical, 3 high, 3 medium, 2 low)
  wrote ./intuneatlas.sarif
  exit 1  — 6 findings at or above `high`
.github/workflows/tenant-drift.yml yaml 
on:
  schedule: [{ cron: "0 7 * * 1" }]

jobs:
  drift:
    runs-on: ubuntu-latest
    steps:
      - uses: intuneatlas/scan-action@v1
        with:
          baseline: cis-l1
          fail-on: high        # exit non-zero at high or critical
          notes: ./intune-notes.yml

Project status

Alpha, and honest about it.

Windows coverage is solid because that's where the contributors' fleets are. Apple and Android are thinner. Here's exactly where things stand at v0.0.3.

  • Windows configuration & update ringsFull CSP path resolution, conflict detection, settings catalog stable
  • Compliance policies & tenant defaultsEvery platform, Linux included, setting by setting, with actions for noncompliance. Including the secureByDefault check that catches unmanaged devices stable
  • Enrollment, ADE tokens, certificate expiryExpiry warnings for ADE and APNs stable
  • macOS & iOS payloadsIndexes and reports, but payload key mapping is incomplete, so some settings show a raw identifier partial
  • Android EnterpriseWork profile restrictions only. Fully managed and dedicated devices are not mapped yet partial
  • Write-back / push staged changesOne reviewed change at a time, with a write permission you add yourself. Refused if the tenant value moved on; recorded in the setting's history. Rollback does not exist yet new
  • App protection & Conditional Access policiesOut of scope for now. Different object model, would deserve its own index not planned

Contribute

Baseline annotations and platform coverage, mostly.

Two contributor paths. Annotating a baseline needs tenant experience and no TypeScript; extending platform coverage needs the opposite. Both are wanted.

#212 Map remaining com.apple.applicationaccess payload keys to friendly names good first issue #198 Android fully-managed device restrictions are not indexed platform #186 Add CIS Level 2 rules for Windows 11 24H2 attack surface reduction good first issue #174 Rollback for deployed changes behind --experimental-write core
Citations

Every rationale needs a citation: a benchmark section, vendor guidance, or a documented tenant observation. "It's more secure" isn't reviewable, and an annotation nobody can trace gets removed the first time it flags something on someone's fleet that turns out to be fine.
